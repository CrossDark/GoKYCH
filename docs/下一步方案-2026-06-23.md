## 二、关键策略选择

既然未上线可大胆改,以下 4 个决策点需要先拍板(影响后续所有动作):

### 决策 1:要不要重设计数据库 schema?

**选项**:
- **A. 大改 schema**(推荐):直接建新表结构,支持插件/主题/WebAuthn/外部站/扩展字段。一次到位。
- **B. 增量加表**:在现有 13 表基础上加 4-6 张新表,不动旧表。安全但 schema 割裂。
- **C. 维持现状**:只补应用层,schema 不动。限制扩展。

**我的建议**:**A**。既然允许丢数据,大改 schema 是最干净的路径——增量加表会让 bug 审查里的"评论/通知字段无长度限制""CHECK 约束""级联删除"等问题继续在新表里重演。

### 决策 2:要不要换密码方案?

PyKYCH 用 PBKDF2-SHA256(60万次),GoKYCH 用 bcrypt(cost 12)。

**两种都是行业标准**,安全性都够。**建议保持 bcrypt 12**——bcrypt 在硬件加速场景下比 PBKDF2 更抗暴力破解,且 Go 标准库 `golang.org/x/crypto/bcrypt` 实现成熟。**这是设计差异不是 bug,不修。**

### 决策 3:要不要实现插件/主题系统?

PyKYCH 的插件系统(`plugins_sys/`)和主题系统(`themes_sys/`)是大头工程。

**选项**:
- **A. 完整实现**(高投入,1-2 周):用 Go 的 `plugin` 包或自研脚本钩子
- **B. 只做主题**(中等投入,2-3 天):纯 CSS + 模板变量切换,不开放第三方
- **C. 不做**(省事):观感上用户用默认主题即可

**我的建议**:**B 起步**——主题是观感的核心,纯 CSS 变量切换能实现"切肤"效果,无需第三方加载机制。如果后期需要第三方插件再补 A。

### 决策 4:WebAuthn / 外部站 / 全面导入?

这三个都是 PyKYCH 的高级特性,工程量都很大(各 1-2 周)。

**我的建议**:**P2-P3 阶段做,不在本轮大改范围**。本轮聚焦"观感对齐 + bug 修复",这 3 个特性属于"功能扩展",放到后续 sprint。

## 三、阶段化实施路径

### 阶段 1:数据库重设 + 核心 bug 修复 (3-5 天)

**目标**:既然丢数据,就把 schema 一次性到位,顺便消化 bug 审查的 8 项 🔴。

**动作**:
1. **新 schema**:`internal/core/schema/schema.go` 重写,包含:
   - 现有 13 张表 + 加 4 张:`plugin_metadata`、`theme_metadata`、`external_sites`、`webauthn_challenges`(让 webauthn_credentials 表活起来)
   - 现有 13 张表的小修:
     - `articles.content` 加 `MAX LENGTH` 校验(应用层)
     - `comments.content` `VARCHAR(500)` → 保留 + 应用层校验
     - `notifications.title/content` 应用层长度校验
     - `subsite_links.url` 应用层 scheme 白名单
     - `articles.type` 在所有查询入口校验(消除不一致)
2. **静态资源 + 文件上传路由**:
   - `internal/api/files.go` 新增:POST 上传(白名单 MIME + 大小限制 + SHA256 重命名)、DELETE 删除
   - `cmd/gokych/main.go` 加 `r.Static("/uploads", "./data/uploads")` 和 `/static` `/avatars` 路由
   - `data/uploads/` 加入 `.gitignore`
3. **HTTP Server timeout**:`main.go:85-88` 加 `ReadTimeout=10s WriteTimeout=30s IdleTimeout=120s`
4. **X-Request-ID 校验**:`requestid.go:20` 加正则校验
5. **getArticle 改 fail-fast + 304 短路**
6. **content length 校验**:评论/通知/链接描述加 maxLen
7. **Subsite URL scheme 白名单**

**消化 bug 审查**:🔴 2,3,4,5,6,7,8 共 7 项 + 部分 🟡 13

### 阶段 3:内容安全 + 主题系统 (3-4 天)

**目标**:修 XSS 注入 + 主题切换 UI(观感"切肤"体验)。

## 六、风险提示

1. **阶段 1 schema 大改**会影响所有现有数据。**既然允许丢数据,这是可接受的**;但生产前要确保导出的数据快照在某个地方保留。
2. **DOMPurify 集成**会增加前端 bundle size(~50KB gzipped)。可以接受。
3. **主题系统**涉及 CSS 变量全栈改造,工作量比预期大。建议先做基础 1-2 个主题(浅/深),后续扩展。
4. **WebAuthn / 外部站 / 插件系统**都不在本轮大改范围。观感上 GoKYCH 已经能跟 PyKYCH 抗衡,**这些是加分项不是必备项**。
5. **bcrypt vs PBKDF2**:保持 bcrypt 不影响安全性,但用户在 PyKYCH 文档看到 PBKDF2 时可能产生疑虑。如果用户问起,可以解释。
